# v0.5 Provider Plane Validation

## Status

Provider Plane implementation is locally complete and Release-build validated. Physical deployment of v0.5 is not claimed because the connected reference iPhone still runs the previously installed v0.3 daemon and the current execution policy blocks host-driven executable replacement/install before the command reaches the device.

## Local validation

The following pass on the current Mac:

- `control_plane_test: PASS`
- `provider_registry_test: PASS`
- `http_contract_test: PASS`
- `RootTools contract tests: PASS`
- iOS 16 Release `BUILD SUCCEEDED`

Provider tests cover:

- registry enumeration;
- capability bindings;
- provider availability projection;
- DEB -> Procursus package planning;
- IPA/TIPA -> TrollStore package planning;
- package policy excludes raw shell/arbitrary executables;
- provider catalog and package-plan HTTP contracts;
- feature negotiation through `/v1/hello`.

## Reference-device facts already observed

The existing physical iPhone remains reachable and reports the underlying mechanisms needed by the v0.5 registry:

- iPhone14,3 / iOS 16.3.1 (20D67)
- Dopamine rootless jailbreak active
- `/var/jb` bootstrap present
- RootTools daemon UID 0
- SSH reachable
- Frida reachable
- ZXTouch reachable

These facts prove the mechanisms exist but do **not** count as physical verification of the new v0.5 provider endpoint or receipt schema.

## Physical acceptance still required

After v0.5 is deployed:

1. `GET /v1/hello` reports `daemonVersion=0.5.0`, `providerRegistry=true`.
2. `GET /v1/providers/catalog` reports expected provider states on the real device.
3. `POST /v1/package/plan` resolves DEB and IPA/TIPA correctly.
4. A safe semantic action receipt records its expected `providerId`.
5. A deliberately unavailable-provider fixture/future device fails with `provider_unavailable` before execution.
6. Existing Control Plane, lock-aware automation, TCC, lifecycle, and UID501/UID0 separation regressions remain green.
