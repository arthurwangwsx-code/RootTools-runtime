# v0.12 Principal Grants Validation

## Product invariant

A named command principal is an identity, not an authority bundle. New principals begin with zero grants.

Persistent grants:

- are exact capability IDs;
- may target only compiled R0/R1 capabilities;
- may have an expiry timestamp;
- are checked for both read endpoints and Command Gateway mutations;
- do not make R2 self-confirmable;
- can never expose R3 or raw privileged shell.

## Automated acceptance

- Principal store unit test covers zero-default authority, grant, expiring grant, ungrant and grant catalog.
- HTTP contract proves an ungranted principal receives a formal `principal_grant_required` denial receipt for mutations.
- HTTP read contract proves `/v1/status` is denied until `device.status.observe` is granted.
- Owner grant of R0/R1 makes the same principal request succeed without changing the principal credential.
- Attempting to persistently grant `device.process.terminate` is denied because it is R2.
- Owner ungrant immediately removes authority.
- Principal revocation still invalidates the credential itself.

## UI and host tooling

The Agents screen exposes a per-principal Capability Grants page grouped by R0 and R1. The host CLI exposes `principal-grants`, `principal-grant`, and `principal-ungrant`.

## Deferred scope

v0.12 intentionally does not add one-shot R2 approvals or resource-specific constraints. Those are separate approval/grant types rather than overloaded persistent grants.
